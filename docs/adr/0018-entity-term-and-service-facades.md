# ADR 0018: The entity term, and library facades in `services/`

Status: accepted under the owner's word of 2026-11-24 (the release round, released as `v1.17.0`).
The decisions are the owner's rulings of 2026-11-23; the rows marked ▲ are the session's. Amends [ADR 0012](0012-next-spa-tree-colocated-scss.md) (its `services/` line) and
[ADR 0013](0013-owner-folder-rules-and-signup.md) F2 ("a pure utility facade is `shared/utils/`")
and F9 (where the zod, `clsx` and `date-fns` facades live). Catalog release after `v1.16.1`: a
major of `server/bun-express`, `server/python-fastapi`, `serverless/cloudflare`, `frontend/react`,
`frontend/next`, `frontend/vue` and `frontend/angular`, and a patch of `frontend/astro`.

## Context

Two words named one noun. The harness's naming rule, `models/<entity>/` on every template and the
Astro and Next agents files said "entity"; `api/<module>/`, the heading `Adding a module`, the lint
messages of the three server templates and the React, Vue and Angular agents files said "module".
The sample a developer copies was itself named `module` (`api/module/`, `/api/module`, table
`module`), so the word could not go while the sample kept it.

The owner, 2026-11-23: "i don't like the "module" terminology, i'd prefer to name it "entity"",
and "every item that has a need for router, controller, service, model, db table/collection is an
entity".

Reading the frontends for that word showed two more double uses:

1. **"Facade".** Vue and Angular said "one facade per server module over the generated SDK" for
   `user.service.ts`, and "an external library is imported only by its facade" for
   `validation.ts`.
2. **Where a library facade lives.** Astro: `services/<name>.ts`. Next: facades with I/O in
   `services/`, "a date or formatting facade" in `shared/utils/`. React, Vue and Angular: zod's
   in `shared/utils/validation.ts`. ADR 0013 F2 wrote the split down ("a pure utility facade is
   `shared/utils/`").

The owner, the same day: "services may also include facades, for example a luxon wrapper named
time.ts", and "facades belong in services".

## Decisions

### E1. An entity

A domain noun and everything named for it: the route `/api/<entity>`, the directory
`api/<entity>/` (`routes`, `controller`, `schema`, `service`, and `model` where an engine has
one), `models/<entity>/`, the table or collection `<entity>`, and on a frontend
`services/<entity>.*` and `models/<entity>/`. It has the files it needs.

- ▲ `auth` and `health` are entities; `health` is a thin one (routes and a controller). No
  second word names a directory under `api/`.
- ▲ The admin namespace keeps its shape: `api/admin/<entity>/`, an entity like any other.
- "Module" stays in its language sense only: an ES or Python module, `type="module"`, tsconfig's
  `module`, import-linter's `source_modules`, "the env module", "module scope".

### E2. The sample is named `entity`

`api/module/` → `api/entity/`, `models/module/` → `models/entity/`, the route `/api/entity`, the
table `entity` and its index `entity_created_at_id_idx`, the test files, and the identifiers with
their case kept (`ModuleRecord` → `EntityRecord`, `createModule` → `createEntity`, `moduleTable` →
`entityTable`, `listModules` → `listEntities`). It ships in the release that changes the word.

- ▲ The Postgres overlays' first migration is edited in place; a template ships its first
  migration, never a migration of one. Cloudflare's is regenerated by the template's command.
- ▲ Each contract and each frontend's generated client is regenerated by its own command, never
  edited.

### E3. The heading

`Adding a module` → `Adding an entity` in each server template's agents file and in
`SERVER_AGENTS_HEADINGS`. The harness cites it by name; it names the older heading beside it for
as long as it accepts older catalogs.

### E4. The frontends' words

- `services/<entity>.service.ts` (`.api.ts` in React, `.ts` in Next and Astro): "a read or write
  on an entity", "one service per entity over the generated SDK".
- ▲ A directory under `pages/` is a page folder, written `pages/<name>/`: "one directory per
  entity or screen group". `home/`, `not-found/` and `forbidden/` are a screen group, never an
  entity. "A page folder never imports another one."

### S1. A facade

A file that wraps an external library, and nothing else, is a facade. It lives flat in
`services/`, named for what it does (`validation.ts`, `date.ts`, `time.ts`), never for an entity.
An entity's `services/<entity>.*` is a service, not a facade.

- ▲ A library is an npm package. A helper over a platform API, or over nothing, stays in
  `shared/utils/` (`next-path.ts`, `initials.ts`, `storage.ts`, `phone.ts`, `relative-time.ts`,
  Vue's and Angular's `time.ts`).
- ▲ A library wrapped as a component stays a component: `shared/components/icons.ts`, the
  toaster, the UI kit folder, the form folder, Next's theme. Vue's service-worker library stays in
  its store (ADR 0013 F9).

### S2. The facade tier

`shared/` may import only `shared/` and `models/`, and `services/` imports `core/config`; the
validation facade is imported by `shared/components`, `shared/validators` and `core/config`. So a
facade in `services/` has a rule of its own:

- A facade is a file directly in `services/` that the lint config names as the one importer of a
  library. It imports its library and `models/` types, nothing else of the app.
- Every layer may import a facade, `shared/` and `core/config` included.
- Every other file in `services/` (an entity's service, `api.ts`, `call.ts`, `client.ts`,
  `api-error.ts`, `with-copy.ts`) keeps its rule; `shared/` still cannot import one.
- ▲ One lint category, keyed on the listed file names and added once to each layer's allow-list.
  The lint test of each frontend holds three cases: `shared/` importing a facade (allowed),
  `shared/` importing an entity's service (refused), a facade importing `core/config` (refused).

### S3. What moves

- React and Next: `shared/utils/validation.ts`, `date.ts` and `cn.ts` → `services/`.
- Vue and Angular: `shared/utils/validation.ts` → `services/`.
- Astro: nothing; `services/validation.ts` is already there.

The owner on `cn.ts`, 2026-11-23: yes, it moves; one rule with no exception by size.

## Alternatives considered

- **The word alone, the sample left as `module`.** Docs and lint messages only, no major. Refused:
  the old word would survive in the first directory a developer copies.
- **A real noun for the sample (`item`, `note`).** It reads as product code and costs the same
  majors.
- **`services/facades/`.** Obvious on disk and a trivial lint pattern; one more level, and Astro's
  flat `services/validation.ts` would move. Refused for the flat form the owner named.
- **Opening all of `services/` to `shared/` and `core/config`.** No new rule; a shared control
  could then call the API, and `core/config` and `services/` would import each other.
- **Two releases, the word first.** A lint regression in the facade tier could not hold the
  rename; two release rounds. Refused: two pull requests in one release.

## Consequences

- A project generated before this release keeps `api/module/` and `Adding a module`; nothing
  renames it. Each server template's changelog lists the sample's renames for a developer who
  does it by hand, and each frontend's lists the moved files.
- On Next and Astro a facade and an entity's service cannot be told apart by file name
  (`services/time.ts`, `services/user.ts`); the lint config's list is the record.
- A facade added without its lint line is refused from `shared/`: the safe side.
- React and Vue import the validation facade first in the entry file for the CSP (`jitless`);
  the tests that pin that order pin the new path.

## Out of scope

- The `api/` folder and the file names `routes`, `controller`, `schema`, `service`, `model`.
- ADRs 0001 to 0017 and existing changelog entries: history keeps its words.
- The harness's own text, which its plan 031 carries.
